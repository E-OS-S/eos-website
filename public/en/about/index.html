What this project is, who runs it, and the rules it holds itself to.

What E-OS is

E-OS is a distribution of Redox OS with a trust chain added: verified boot, a hybrid-signed package index, a curated desktop. The operating system itself is Redox — the kernel, the C library, the filesystem and the drivers come from upstream, some of them through forks that carry E-OS patches and are kept rebasable.

It is not Tails, not Qubes OS and not GrapheneOS. Those solve different problems, and comparing E-OS with them would be unfair to a reader trying to choose. The comparison that makes sense is with Redox itself: E-OS is Redox with a chain of trust that can be checked.

How the ecosystem is organised

Thirty repositories in one manifest, each pinned by revision. GitLab is the source of truth and GitHub is a read-only mirror. Mistaking one repository type for another is the most expensive mistake available in this project, so the type is a field that continuous integration enforces, not a sentence in a document.

Who runs it

One maintainer. That is stated in the security policy too, because it is information a person needs when deciding how to disclose a vulnerability, or how much to depend on the project.

There is no company behind E-OS, no legal entity and no funding. The copyright line reads "Damian (Gh0s777tt) and the E-OS contributors", and the whole is licensed under AGPL-3.0-or-later.

The rules this project holds itself to

These are not aspirations. Each of them exists because its absence broke something that then had to be found the hard way.

  • A check that cannot fail is not a check. Every gate carries a negative test that has been seen going red.
  • Verify the artefact, not the exit code. A green build has repeatedly meant a binary that was two months old.
  • Fail closed by default. An exception needs an explicit environment variable, and the summary says what it skipped.
  • Measure, do not infer. A conclusion drawn from one directory is not a conclusion about every source.
  • Correct your own published conclusions in the open, with the correction next to what it replaces.
  • Documentation changes in the same merge request as the thing it documents, never in the next one.

What this project does not claim

Stated here so that nobody has to work it out from what is missing.

  • It does not claim to have been audited by anyone outside the project.
  • It does not claim reproducible builds. That is a goal; the comparison has not been run.
  • It does not claim to run on your hardware. Nothing has been booted on a physical machine yet.
  • It does not claim compatibility with Linux binaries or a stable syscall surface. The ABI is inherited from Redox and still moves.
  • It does not claim endorsement by the Redox OS project.

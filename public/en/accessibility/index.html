Accessibility

What this site does for keyboard and screen-reader use, which of those claims a gate measures on every build, and which are only a person's word.

Claims, and how each one is checked

A claim without a check is a hope. The right-hand column says which is which.

Accessibility claims for this website
ClaimHow it is checked
Colour contrast meets the ratios stated belowMeasured on every build by scripts/check-contrast.mjs against the design tokens; the build fails below the declared minimum.
Every visible string is translatableMeasured by scripts/check-i18n.mjs, which fails on a bare literal in a text position or in aria-label, alt, title or placeholder.
Landmarks and headings are structuralReviewed by hand, not automated. Written as real header, nav, main and footer elements with accessible names.
The keyboard reaches everythingReviewed by hand in Safari and Chrome on macOS. Not automated.
Reduced motion is honouredA prefers-reduced-motion rule in the stylesheet removes transitions and smooth scrolling. Not automated.
Screen-reader reviewNot done. Written here as not done rather than left out.

Contrast

Body text must reach at least 7:1 against its background, links at least 4.5:1 and secondary text at least 4.5:1. The crimson accent measures 4.27:1 on the dark background: enough for rules, borders and large display type, not enough for body text. So it is never used for body text, and a lighter crimson at 7.40:1 carries the links.

Those minimums are read from the same file the gate reads, so this page cannot claim a ratio the build does not enforce. Run it yourself:

npm run check:contrast

Keyboard

  • A skip link is the first focusable element on every page and becomes visible when it takes focus.
  • Focus is always visible: a two-pixel outline in a colour measured against both themes.
  • The theme control is a button, reached with Tab and operated with Enter or Space.
  • The ticket composer is an ordinary form. Every field has a label, and the result is a link you follow deliberately, never an automatic submission.
  • Nothing traps focus. There are no modal dialogs, carousels or infinite scrolls on this site.

Motion

There are no animations, no autoplaying media and no parallax. Smooth scrolling is the only motion the stylesheet asks for, and prefers-reduced-motion removes it outright, along with every transition, rather than merely shortening them.

Structure

The page skeleton is the same everywhere:

  • One h1 per page, then h2 sections in document order. No heading level is skipped for a visual effect.
  • header, nav, main and footer are real elements, and every nav has an accessible name, so a screen reader can tell the main navigation from the language switcher and from the footer groups.
  • Tables have a caption and row or column headers. They are never used for layout.
  • The page language is declared with a full BCP-47 tag, and each language link declares the language it leads to.

Not verified

Listed rather than omitted:

  • No screen-reader pass has been done with NVDA, JAWS or VoiceOver.
  • No automated audit (axe, Lighthouse, pa11y) is wired into the build yet.
  • Contrast is measured between design tokens, not against rendered pixels, so an inherited colour somewhere could still be wrong.
  • The site has not been tested at 200% zoom or with a browser text-size override on a small screen.
  • Polish and English are the only locales. No right-to-left language has been laid out, although the stylesheet uses logical properties where it matters.

If something blocks you

Open a documentation ticket saying what you were trying to do, what you used and what happened. An accessibility barrier is a defect, not a feature request.

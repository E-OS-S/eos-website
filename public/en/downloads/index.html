Developer-only

Downloads

Developer-only for now. This page says what that means on a static host, and what it cannot mean.

What developer-only means here

The owner's decision on 2026-09-03 was that downloads stay closed to developers until further notice. This site is served by GitLab Pages, which serves files and runs nothing: it cannot ask who you are, so it cannot enforce a gate.

So the gate is not a switch that hides links from you. It is the absence of the links: while the flag below is true, no artefact URL is written into this page at all. A client-side "are you a developer?" toggle would be decoration, and this page will not pretend otherwise. A real gate needs the server-side identity service that is still a roadmap row.

Configuration flag downloads.developerOnly = true

There are no download links on this page

Deliberately. The reasons are worth stating, because they are also the reasons the flag has not flipped yet:

  • Nothing has been booted on physical hardware. Publishing an image implies it is meant to be run on a machine that has never been tested.
  • The x86_64 image ships with no active package source, so an installed system cannot receive a fix through the update mechanism.
  • There is no ISO and no cosign signature. Release artefacts carry a minisign signature over a SHA256SUMS file.
  • A real download gate needs a server-side identity check, and that does not exist yet.

Build it instead

The build is reproducible in the sense of "it runs", not yet in the sense of "byte for byte". It needs podman and roughly 37 GB of build cache.

git clone https://gitlab.com/e-os/e-os.git
cd e-os
bash scripts/eos-build.sh x86_64

Developer documentation

What is already public

Honesty requires saying that some things are downloadable today, even though this page publishes nothing:

  • The signed aarch64 package index is public on GitHub Pages and answers with HTTP 200. The x86_64 index answers 404.
  • Nightly images exist as continuous-integration job artefacts with a one-week retention.
  • A GitHub release object exists for v0.1.0 only. v0.2.0 is an annotated, signed tag with no release object behind it.

If you do get an image, verify it

The steps that matter, in order:

  1. Check the SHA256SUMS file against the raw image, not against the compressed transport wrapper.
  2. Verify the minisign signature over SHA256SUMS with the published public key before trusting any digest in it.
  3. If you boot under Secure Boot on a machine that is not yours to reconfigure, expect to enrol the E-OS certificate first. It travels on the installation medium at EFI/EOS/eos-secureboot.der.
  4. After installation, check that the trust anchors under /etc/pkg/ match the published public halves.

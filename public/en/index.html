E-OS

A hardened downstream distribution of Redox OS

E-OS is a distribution of Redox OS, a Unix-like operating system whose microkernel is written in Rust. It is not written from scratch: the kernel, the C library, the filesystem and the driver stack come from Redox, and E-OS adds a verified boot chain, a package index signed with a hybrid ed25519 + ML-DSA-65 signature, a per-user kernel-scheme allowlist and a curated desktop. It is also not finished. The x86_64 image currently ships with no active package source, so a fix released today cannot reach an installed x86_64 system through the update mechanism; the browser in the image is an upstream prebuilt rather than the hardened build its recipe describes; and it is a single-maintainer project. Everything on this site that says something was measured names what was measured and when.

What has been verified

Each row was checked against a built artefact — an image that was mounted, an index that was verified, a machine that reached a login prompt — not against the source that was supposed to produce it.

Verified properties, with the measurement behind each
PropertyWhat was measured
Verified boot chainThe bootloader authenticates the kernel and the initfs with ed25519 over SHA-512(role, length, data) before the magic-byte check and before any byte is used. A missing signature or a zero key refuses to boot, and domain separation means a signed initfs cannot verify as a kernel.
Post-quantum signed package indexrepo.toml carries a hybrid ed25519 + ML-DSA-65 (FIPS 204) signature. Checked against the live aarch64 index of 79 packages: both halves verify, and one flipped byte makes both refuse.
Package bytes bound to the signed indexThe blake3 digest from the authenticated manifest is checked against the bytes about to be extracted, on every install path including pkg install. The serial and expires fields give rollback and freeze protection.
Secure BootBoth UEFI bootloaders carry SBAT and are Authenticode-signed, with SBAT stamped before signing because Authenticode covers the whole file. The installation medium carries the E-OS certificate as DER at EFI/EOS/eos-secureboot.der, because a firmware menu is where it is needed.
Boot to a login promptboot-smoke reached userspace login on x86_64 and on aarch64, exit 0, measured 2026-09-01.
Install, end to endPartition, install, reboot, login proven once and re-proven after the shared-interrupt fix. The encrypted path is exercised with a deliberately wrong password that has to fail before the correct one is allowed to work.
Per-user kernel-scheme allowlist/etc/login_schemes.toml grants root everything and the unprivileged account an explicit 25-scheme list. Raw IP sockets are removed from that list.
User-space drivers16 drivers run as ordinary processes, so a driver fault does not take the kernel down. Without an IOMMU this is process isolation, not hardware isolation, and the roadmap says so.
Full-disk encryptionRedoxFS AES-XTS, offered by the installer. Hardware-accelerated on aarch64 through the ARMv8 crypto extensions; a software path on x86_64.
Forced first-boot passwordThe text login and the graphical greeter both refuse to continue while the account has no password.

What is not true yet

The same page has to carry both halves, or the first half is advertising.

  • The x86_64 image ships with no active package source: both entries in /etc/pkg.d/ are commented out, so an update cannot reach an installed x86_64 system.
  • The browser in the image is the upstream NetSurf 3.11 prebuilt, not the position-independent build its recipe describes — readelf reports type EXEC at 0x400000, measured 2026-09-02.
  • Passwords set in the running system are hashed with argon2i at m=4096, t=3 — 4.0 ms per guess against the 14.1 ms of the argon2id used at image-build time. Two paths, and the stronger one is not the one a user gets.
  • A reproducible build has not been demonstrated. The same commit has never been shown to produce the same image byte for byte.
  • Nothing has been verified on physical hardware. QEMU does not prove that firmware will boot the medium or that a driver will bind a real chipset.
  • There is no ISO release, no cosign signature and no published PGP key. Release artefacts carry a minisign signature over SHA256SUMS.
  • The desktop applications have no automated tests at all, and no host window backend, so they type-check off Redox but do not open a window there.
  • It is a single-maintainer project. That matters when deciding how much to depend on it.

Built on Redox OS

Substantial parts of E-OS — the kernel, relibc, RedoxFS, the driver stack and the cookbook build system — come from Redox OS and remain under the MIT licence. E-OS is an independent downstream distribution: it is not official Redox OS software and it is not endorsed by the Redox OS nonprofit.

Privacy and security

How to report a vulnerability, what the trust chain actually does, where it does not reach, and what this website knows about you.

Reporting a vulnerability

Do not open a public issue. Two private channels, both monitored:

  • GitHub Security Advisories — a private thread and a route to a CVE
  • Email the maintainer

No PGP key is published for this project. Do not encrypt to a key you find elsewhere claiming to be ours; use Security Advisories, which is private without needing one.

The full security policy

Response targets

Targets from a single maintainer, stated as targets and not as a contract. If a deadline is going to be missed you are told before it passes, with the reason.

One caveat has to be stated plainly: the x86_64 image ships with no active package source, so a fix released today cannot reach an installed x86_64 system through the update mechanism.

What the trust chain does

Each of these was checked against a built artefact, not against the source that was supposed to produce it.

  • The bootloader verifies the kernel and the initfs by ed25519 signature before the magic-byte check and before any byte is used. Domain separation means a signed initfs cannot verify as a kernel.
  • The package index is signed with a hybrid ed25519 and ML-DSA-65 signature. Both halves must verify, and a single flipped byte makes both refuse.
  • The trust anchors are pinned inside the image and are byte-identical to the committed public halves.
  • Package bytes are checked against the blake3 digest in the authenticated manifest before extraction, with serial and expiry fields for rollback and freeze protection.
  • Both UEFI bootloaders carry SBAT and are Authenticode-signed, with SBAT stamped before signing because the signature covers the whole file.

Where it does not reach

A trust chain that is only described is not a trust chain. These are the parts that are described but not yet true.

  • No IOMMU. Drivers are separate processes, which is process isolation, not hardware isolation.
  • Application sandboxing is planned, not shipped: the containment package is disabled and per-application policy does not exist.
  • There is no persistent audit log and no packet filter.
  • Passwords set in the running system are hashed with argon2i at m=4096, t=3 — weaker than the argon2id used when the image is built.
  • Signing keys live on the build host, not in a hardware security module or on a token. Key custody is a roadmap row blocked on hardware.
  • Nothing has been verified on physical hardware, so the boot chain is proven under QEMU and its firmware only.

What this website knows about you

Nothing that reaches the project. This site is static files with no analytics, no cookies, no trackers and no third-party fonts or scripts. The only browser storage it uses is a single localStorage entry holding your light or dark preference, which never leaves your device.

The host that serves the files sees your request the way any web server does, under its own operator's policy. If you follow a link to GitLab, GitHub or Redox OS, their policies apply from that point onwards.

Security questions

Has E-OS been audited?
Not by anyone outside the project. There are internal audit reports in the repository with dates and methods; they are self-assessments and say so.
Is it post-quantum?
The package index signature is hybrid ed25519 and ML-DSA-65, so that one surface is. Nothing else in the system is, and the phrase should not be applied to E-OS as a whole.
Can root do anything?
Not by construction. Access depends on the kernel scheme capability set rather than on the user id, which was measured by watching sudo and root fail identically on a denied scheme.
Is there a bug bounty?
No. There is no funding behind the project.
How do I check that the image I have is the image you published?
SHA256SUMS carries the digests of the raw images and a minisign signature covers that file. Verify the signature first, then the digest against the raw image rather than against the compressed download.
